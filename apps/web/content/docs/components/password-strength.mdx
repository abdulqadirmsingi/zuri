Use `PasswordStrength` when someone is **creating or changing** a password. It shows how strong the password is as they type, and which requirements are still unmet. Don't use it for signing in: a login field should be a plain password input.

The text is scored on the device. Nothing is sent anywhere, and the component never stores or logs the password.

## Installation

<InstallTabs name="password-strength" />

This also installs [Button](/docs/components/button) and [Input](/docs/components/input), which it is built from, and adds two small keyframes (`zuri-rise` and `zuri-shake`) to your CSS.

## Usage

```tsx
import { PasswordStrength } from "@/components/ui/password-strength";

<PasswordStrength
  label="New password"
  name="password"
  required
  hint="Longer is stronger. A short phrase works well."
/>
```

It works uncontrolled (`defaultValue`) or controlled (`value` with `onValueChange`, which also receives the score).

## Showing an error

Pass `error` when you refuse the password. It is announced when it appears, the field is marked invalid, and the field shakes once.

## Scoring

`scorePassword(password, checks, options)` is exported on its own, so you can use the same rules on a form that does not use the component, and test them.

- The level (1 to 4) follows how many of the requirements pass.
- It is **capped at 1** if the password is shorter than `shortLength` (default 8) or is a very common password, including one with digits or symbols tacked on (such as "Password123").
- It is **capped at 2** if it uses fewer than five different characters (such as "aaaaaaaaaaaa1!").
- Characters are counted the way people see them, so an emoji counts as one.

The default requirements put length first, as current guidance (NIST SP 800-63B) does: at least 10 characters, upper and lower case, a number, and a symbol or space. Change them with `makeChecks(minLength)` or pass your own list.

```tsx
import { makeChecks, PasswordStrength } from "@/components/ui/password-strength";

<PasswordStrength label="Password" checks={makeChecks(14)} />
```

## Accessibility

- The input has a real label, `autocomplete="new-password"` (so password managers offer to generate one), and spell-check and auto-capitalisation are off.
- The strength is a `role="meter"` with a text value ("Strong"), so it is more than colour. Each requirement says "met" or "not met" in words as well as showing a tick.
- The show/hide button is a **pressed toggle** with a name that does not change ("Show password"). It is at least 32 pixels square.
- The hint, the error and the requirements list are linked to the input with `aria-describedby`. An error uses `role="alert"`.
- A polite summary ("Strength: Good. 3 of 4 requirements met.") is announced after typing pauses, not on every keystroke.
- The meter fills, the ticks draw and the word rises using the `--duration-*` tokens, which are almost zero under `prefers-reduced-motion`, so nothing moves for people who ask for that. The shake is skipped too.

## Tokens used

`--muted`, `--danger`, `--warning`, `--success`, `--foreground`, `--muted-foreground`, `--control-border`, `--duration-fast`, `--duration-base`, `--duration-slow`, `--ease-out`.

## Known limitations

- It is a rule-based estimate, not a measure of how guessable a password really is. It has a tiny built-in list of very common passwords, not a breach database. **Always validate on the server too**, ideally against a breached-password service.
- Rules that ask for symbols and mixed case can push people towards predictable patterns; that is why length comes first in the defaults.
- There is no "confirm password" field. Compose a second [Field](/docs/components/field) for that.
- No translations are bundled; pass your own through `messages`.
- It is a client component, because it holds the typed text and the show/hide state.
